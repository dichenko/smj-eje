# Smart-J: личные отчеты на VPS

Отдельный проект для постоянного просмотра отчетов Smart-J: занятия по Matata, Kids, UserBasic и Junior, фильтры по городам, преподавателям, группам и датам, недельные отчеты с календарем. В приложении также ведутся видеоотчеты по занятиям и контакты координаторов. Интерфейс на русском, подходит для телефона, не требует внешних CDN или JavaScript.

Приложение получает данные через авторизованные страницы Smart-J, сохраняет их в SQLite и показывает отчеты независимо от доступности источника. Оно не изменяет данные в Smart-J и не отправляет уведомления.

## Видео и преподаватели

Раздел «Видео» хранит отдельные запросы по каждому наблюдению: город, преподаватель, координатор, даты запроса и отправки, модуль, ссылка на видео, что хорошо и зона роста. Можно добавить несколько видеозаписей одного преподавателя, открыть ссылку, изменить запись и скачать отдельный Excel-отчет по образцу. Если ссылка и город координатора есть, координатор подставляется автоматически.

В форме видео город известного преподавателя подставляется автоматически из занятий, видеозаписей и контактов; поле города доступно только для чтения. Это работает при переходе по ссылке с именем преподавателя, при смене преподавателя и при сохранении без JavaScript. Если имя встречается в нескольких городах, выберите вариант «Имя — Город» в списке преподавателей. Для нового имени, которого еще нет в базе, можно указать город вручную.

В разделе «Преподаватели» показаны пары город/имя, модули и количество видео. Нажатие на модуль открывает обычный отчет занятий, отфильтрованный по этому преподавателю и городу. Нажатие на количество видео показывает его записи.

Раздел «Координаторы» содержит город, ФИО, телефон, личную почту, корпоративную почту и дату рождения; все поля можно редактировать. Контакты импортируются из JSON через `smj import-coordinators`, который читает массив объектов из stdin и добавляет или обновляет запись по паре город + ФИО. Локальные исходные файлы с контактами исключены из Git.

## Правила данных

- Первая успешная синхронизация загружает все проведенные занятия **с 01.09.2026 включительно**. Прежнюю локальную базу переносить не нужно.
- После первой загрузки изменяем только занятия **младше 7 дней**: сегодня и шесть предыдущих календарных дней в Europe/Moscow. Возраст определяется датой проведения, а не датой загрузки.
- Например, 05.10.2026 изменяемый период — 29.09.2026–05.10.2026. Занятия от 28.09.2026 уже заморожены.
- В этом окне добавляем новые занятия, отражаем исправления и подтвержденные удаления. Когда записи выходят из окна, они становятся неизменными.
- **Старый архив после первой загрузки фиксируется целиком**: поздно появившиеся старые записи также не добавляются. Это согласованное правило, устраняющее неоднозначность между старой правкой и новым занятием.
- Дата начала периода фиксирована; она не сдвигается автоматически в следующем учебном году.

В известных HTML-отчетах нет постоянного ID занятия. Поэтому недавние занятия сверяются как полный набор: изменившаяся запись заменяется, неизменная сохраняется, одинаковые записи учитываются с их количеством. Это позволяет исправлять тему, группу, город, дату внутри окна и преподавателя без объединения разных групп. Счетчики показывают такую замену как добавление и удаление. Если источник предоставляет `data-lesson-id` или `data-event-id`, поддерживается обновление записи по ID; перенос даты определяется по прежней дате занятия. Без ID перенос даты за пределы окна невозможно надежно отличить от исчезновения недавней и изменения старой записи: архив остается фиксированным.

Сбор всех четырех модулей выполняется до изменения базы. Ошибка сети, входа, структуры HTML, даты или любого модуля сохраняет прежние данные. Если за один запуск исчезает больше 50% недавних записей модуля, в котором было не менее 10 занятий, синхронизация блокируется до ручной проверки. Это касается и массовых замен без ID. Подтвержденное большое изменение можно применить командой `smj sync --accept-large-deletions`.

SQLite работает на локальном диске в режиме rollback journal с ожиданием блокировок 15 секунд. Сведения о занятиях хранятся непосредственно в строках: изменение общих справочников не может задним числом изменить архив. Блокировка сборщика принадлежит ядру ОС и освобождается при завершении/падении процесса.

## Локальный запуск

Требуется Python **3.11 или новее**. Windows и Linux поддерживаются; Gunicorn используется только на Linux.

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
.venv/Scripts/smj.exe secrets
```

Сохраните сгенерированные `APP_PASSWORD` и `FLASK_SECRET_KEY` в `.env`, задайте учетные данные Smart-J и для локальной работы измените:

```dotenv
APP_ENV=development
ENV_FILE=.env
DB_PATH=data/reports.db
BACKUP_DIR=backups
```

Пароль и ключ должны иметь не менее 32 символов. Команда `secrets` только выводит новые значения, не сохраняет их автоматически. Реальный `.env` не входит в Git.

```powershell
.venv/Scripts/smj.exe init-db
.venv/Scripts/smj.exe sync
.venv/Scripts/smj.exe serve
```

Откройте `http://127.0.0.1:8081/`. Первый сбор начинается **сразу**, без ожидания таймера. В Linux соответствующие команды находятся в `.venv/bin/`. Встроенный сервер допускается только с `APP_ENV=development`, слушает localhost и работает без debugger/reloader.

По умолчанию код требует HTTPS от источника. В `.env.example` явно включен HTTP для совместимости с существующим `http://my.smart-j.ru`. Он передает учетные данные источнику без TLS. Если Smart-J поддерживает HTTPS, задайте `SMARTJ_BASE_URL=https://my.smart-j.ru` и `SMARTJ_ALLOW_HTTP=false`. Проверка TLS включена; переход на другой хост или HTTP без разрешения запрещен. Эта настройка не влияет на HTTPS вашего поддомена.

## Развертывание рядом с ботом и системным Caddy

Инструкция рассчитана на Ubuntu с Python 3.11+, системным Caddy и свободным `127.0.0.1:8081`. Сначала проверьте `python3 --version`, свободную память, диск и порт. Если версия Python ниже 3.11, установите поддерживаемый Python отдельно; не заменяйте окружение бота.

### 1. Отдельный пользователь, код и окружение

Следующие команды выполняются на VPS. Они не нужны на вашем Windows-компьютере.

```bash
sudo apt update
sudo apt install -y python3-venv git
sudo useradd --system --home-dir /var/lib/smj-eje --shell /usr/sbin/nologin smj
sudo install -d -o smj -g smj -m 0700 /var/lib/smj-eje /etc/smj-eje
sudo git clone https://github.com/dichenko/smj-eje.git /opt/smj-eje
cd /opt/smj-eje
sudo python3 -m venv .venv
sudo .venv/bin/python -m pip install -r requirements.txt
sudo install -o smj -g smj -m 0600 .env.example /etc/smj-eje/.env
sudo .venv/bin/smj secrets
sudoedit /etc/smj-eje/.env
```

Если пользователь уже существует, повторный `useradd` не требуется. Если репозиторий приватный, клонируйте через настроенную авторизацию Git или read-only deploy key; не вставляйте токен в URL. Код и окружение принадлежат root, приложение пишет только в `/var/lib/smj-eje`.

В `/etc/smj-eje/.env` заполните новые `APP_PASSWORD`, `FLASK_SECRET_KEY`, `SMARTJ_USERNAME`, `SMARTJ_PASSWORD`. Для production оставьте пути из примера и `APP_ENV=production`. Сервис принудительно использует production-режим. Перед публикацией проверьте права файла `600` и владельца `smj`.

Службы передают приложению только путь `ENV_FILE`; все секреты читает dotenv внутри процесса. Не добавляйте `.env` как директиву systemd `EnvironmentFile`: это передает пароли и ключи в общие системные переменные окружения.

### 2. Первая загрузка и веб-служба

```bash
sudo install -m 0644 deploy/smj-*.service deploy/smj-*.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo -u smj env ENV_FILE=/etc/smj-eje/.env /opt/smj-eje/.venv/bin/smj init-db
sudo systemctl start smj-sync.service
sudo systemctl status smj-sync.service --no-pager
sudo journalctl -u smj-sync.service -n 30 --no-pager
sudo systemctl enable --now smj-web.service
curl --fail http://127.0.0.1:8081/healthz
```

Сначала проверьте результат первого сбора и данные по четырем модулям. Запуск `smj-sync.service` выполняет сбор сразу. Веб-служба — Gunicorn с одним worker и двумя потоками, автоматическим перезапуском и ограничением памяти 384 МБ. Сборщик имеет отдельный лимит 384 МБ, пониженный приоритет и таймаут 10 минут. При необходимости измените лимиты после измерений, учитывая бот и Caddy.

### 3. Поддомен

Создайте A-запись поддомена на IPv4 VPS. AAAA нужна только при настроенном IPv6. Порты 80/443 должны быть доступны Caddy.

Добавьте отдельный блок из `deploy/Caddyfile.example` в существующий `/etc/caddy/Caddyfile`, заменив `reports.example.com` своим поддоменом. Сохраните остальные блоки и резервную копию конфигурации. Порт приложения наружу не открывайте.

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy получает и продлевает HTTPS-сертификат. Проверку `/healthz` он блокирует снаружи; она доступна только локально. Проверьте вход на поддомене, страницы отчетов и работу существующего бота/webhook. Приложение доверяет ровно одному прокси; upstream должен оставаться закрытым на localhost.

### 4. Production-таймер и резервные копии

```bash
sudo systemctl enable --now smj-sync.timer smj-backup.timer
sudo systemctl list-timers 'smj-*' --all
sudo systemctl start smj-backup.service
```

Таймер синхронизации задает **новый случайный интервал 30–60 минут между стартами**: `OnUnitActiveSec=30min` и `RandomizedDelaySec=30min`, `FixedRandomDelay=no`. После перезагрузки первый плановый запуск — примерно через 1–31 минуту. Сам сайт доступен сразу после старта веб-службы. Интервал относится только к production; при подготовке выполняйте ручные сборы и проверяйте расчет следующего запуска. Не нужно ждать час и не нужно часто обращаться к Smart-J для проверки таймера.

Не включайте старую cron-задачу параллельно. `smj-sync.service` не имеет постоянного автозапуска: ее запускает таймер либо администратор. Веб-служба запускается после загрузки VPS. Перезагрузку общего сервера для проверки согласуйте отдельно из-за бота.

В 04:00 по Москве выполняется согласованная резервная копия SQLite через backup API с проверкой целостности. Хранятся 7 последних ежедневных копий и 4 еженедельные (по воскресеньям). Копии находятся в `/var/lib/smj-eje/backups`; настройте перенос хотя бы одной копии **вне VPS** в ваше защищенное хранилище. Встроенная служба делает только локальные копии.

## Обслуживание

```bash
# Собрать данные сразу; блокировка предотвращает параллельный сбор.
sudo systemctl start smj-sync.service
# Статус и логи: никаких паролей, cookies или сырых HTML в журнале.
sudo systemctl status smj-web.service smj-sync.timer --no-pager
sudo journalctl -u smj-web.service -u smj-sync.service -n 100 --no-pager
# Резервная копия сразу.
sudo systemctl start smj-backup.service
```

На сайте видны время последнего успешного обновления по Москве, общее количество занятий, текущий сбор и неуспешная попытка. После 120 минут без успешного обновления отображается предупреждение. Ошибка Smart-J не блокирует просмотр последних данных. Подробный безопасный результат последнего сбора доступен после входа в `/api/status`.

### Смена пароля

Измените `APP_PASSWORD` в `/etc/smj-eje/.env` и перезапустите `smj-web.service`. Существующие сессии перестанут работать даже при прежнем `FLASK_SECRET_KEY`. Изменение ключа также отзывает сессии. Сессия действует максимум 7 дней, продления на каждом запросе нет. Cookie Secure/HttpOnly/SameSite, формы защищены CSRF. Ограничение входа — 5 неверных попыток с одного IP и 50 суммарно за 15 минут; состояние общее для процессов и сохраняется при перезапуске.

### Подтверждение большого изменения

Сначала проверьте исходные отчеты Smart-J и журналы, затем при необходимости:

```bash
sudo -u smj env ENV_FILE=/etc/smj-eje/.env \
  /opt/smj-eje/.venv/bin/smj sync --accept-large-deletions
```

Этот флаг отключает только порог количества удалений/замен. Проверки полноты модулей, структуры, дат и атомарность остаются обязательными. Сбор все равно не изменяет замороженный архив.

### Обновление

Каждый push в `main` автоматически запускает workflow **Tests and deploy**: проверки на Windows/Ubuntu с Python 3.11/3.13, затем установка проверенного коммита на VPS. Push в другие ветки и pull request запускают только проверки. Из вкладки Actions можно также запустить workflow вручную для `main`.

Деплой использует отдельного пользователя `smj-deploy` и SSH-ключ, разрешающий только команду `deploy <SHA>`. Ключ не дает интерактивного доступа или проброса портов. Административный SSH-ключ и пароли приложения в GitHub не передаются. В Secrets репозитория настроены `VPS_HOST`, `VPS_USERNAME`, `VPS_SSH_KEY`, `VPS_KNOWN_HOSTS`; ключ хоста сверяется строго.

На сервере скрипт `deploy/deploy.sh` блокирует параллельные установки, отказывается перезаписывать локальные изменения и проверяет, что SHA остается последним коммитом `main`. Устаревший запуск пропускается. Перед обновлением останавливаются таймеры и сборщик, создается согласованная резервная копия базы. На время установки сайт останавливается. Новый коммит получает отдельное Python-окружение, зависимости и файлы systemd; после запуска проверяется `/healthz`, затем восстанавливаются ранее работавшие таймеры. Окружения текущей и предыдущей версии сохраняются в `/opt/smj-eje-deploy`.

При ошибке возвращаются предыдущие код, Python-окружение и службы; workflow завершается с ошибкой. База и `.env` остаются вне каталога приложения. База автоматически не откатывается: для несовместимой миграции потребуется восстановление резервной копии по инструкции ниже. Результат установки и ошибки доступны в Actions.

Для первоначальной настройки нового сервера установите код в `/opt/smj-eje`, затем выполните от root `bash deploy/setup-autodeploy.sh /path/to/deployment-key.pub` и сохраните соответствующий приватный ключ в Secrets. После изменения `ssh-dispatch.sh` или `setup-autodeploy.sh` повторите эту настройку: установленный root-owned dispatcher находится вне Git-каталога.

Для ручного запуска той же установки:

```bash
cd /opt/smj-eje
sudo git fetch origin main
sudo bash deploy/deploy.sh "$(git rev-parse origin/main)"
```

Для намеренного отката уже успешно установленного изменения используйте `git revert` и push в `main`: исправление пройдет тот же цикл проверок и установки.

### Восстановление

Остановите веб-службу, таймер, сборщик и службу резервного копирования. Сохраните поврежденную базу для диагностики, затем замените `/var/lib/smj-eje/reports.db` согласованной копией, задайте владельца `smj:smj` и права `600`. Проверьте `PRAGMA integrity_check` через Python sqlite3, снова запустите веб-службу и таймер. В резервной копии сохраняется также признак первой успешной загрузки: архив остается фиксированным.

Для намеренной полной повторной загрузки создайте новую базу после резервного копирования старой. Это заново прочитает весь период и может изменить ранее замороженный архив; обычная синхронизация этого не делает.

Журналы ведутся через journald; его общий лимит диска задается администратором с учетом бота. Не размещайте `.env`, базы, копии или HTML-выгрузки в публичном каталоге. Доступ к SSH — по ключам, изменения firewall должны сохранять текущие правила бота и SSH.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
ruff check .
pytest -q
```

Тесты используют синтетические данные, не обращаются к Smart-J и не содержат реальных логинов или занятий. Проверяются авторизация всех отчетов/API, CSRF, защищенные cookies, смена пароля, общий лимит попыток, экранирование HTML, фильтры, первая загрузка, границы дат и 7 дней, московская полночь, заморозка архива, исправления/удаления, разные группы и одинаковые записи, откат транзакции, отказ источника, блокировка сборщика и восстановление копии.

GitHub Actions запускает проверки на Windows и Ubuntu с Python 3.11 и 3.13; на Ubuntu дополнительно проверяется настоящий запуск Gunicorn. После успешных проверок `main` устанавливается на VPS. Проверки не ждут production-интервала.
